# Instagram投稿用画像 自動加工ツール 設計書

- 作成日: 2026-07-25
- ステータス: 承認済み(brainstormingフェーズ)

## 背景・目的

スマートフォンで撮影したInstagram投稿用の写真は、暗かったり彩度不足だったりすることが多い。背景変更などAI生成感のある加工ではなく、明るさ・彩度・露出を自然に補正し、プロが撮影したような見栄えに近づけたい。手動で毎回加工するのは手間なので、Google Driveの特定フォルダに画像を入れるだけで自動的に加工されて出てくる仕組みを作る。

## 前提・制約

- コストはゼロを目指す(クラウドAPI課金・サブスクリプションなし)
- 写真は iCloud写真同期 → Googleドライブへ手動アップロードという経路で来る
- Google DriveのMCP連携には削除機能がないため、削除を伴う自動化(元画像削除・保持期間切れ削除)にはGoogle Drive API(OAuth)を直接叩くPythonスクリプトが必要
- 「ダウンロードしたら削除」はAPI的に検知不可能なため、日数ベースの自動削除で代替する

## アーキテクチャ

- ローカル(Mac)で動作するPythonスクリプト一式(`photo-enhancer/`ディレクトリ、このリポジトリ直下に新設)
- Google Drive API(OAuth、個人アカウント)でフォルダの読み書き・削除を行う
- 画像加工は Pillow / OpenCV(+ pillow-heif でHEIC対応)をローカルで実行。クラウドAPI不使用のため完全無料
- 実行トリガー: macOS launchd による1日2回の定期実行(22:00 / 23:30) + 手動実行用のCLIコマンド

## Google Driveフォルダ構成

```
Instagram画像加工/(親フォルダ)
├── 加工依頼/   ← ユーザーがスマホ/Driveアプリから画像をアップロード
└── 加工済み/   ← 加工後の画像が出力される
```

## 処理フロー

1. ユーザーが「加工依頼」フォルダへ画像をアップロードする(手動)
2. launchdが22:00・23:30にスクリプトを起動(または手動実行)
3. スクリプトが「加工依頼」フォルダ内の新規画像を検出
4. 各画像について:
   a. ダウンロード
   b. 画像加工を実行(下記「加工内容」参照)
   c. 「加工済み」フォルダへアップロード
   d. アップロード成功を確認できたら、元画像を「加工依頼」から削除
5. 「加工済み」フォルダ内でアップロードから7日経過したファイルを自動削除(安全ネット。基本はユーザーがダウンロード後に手動削除する運用)

## 加工内容(自然な見栄えを目指す)

- オートホワイトバランス(グレーワールド法)
- ヒストグラムベースのオートレベル補正(白飛び・黒つぶれの解消)
- ガンマ補正による露出(明るさ)調整
- HSV空間での彩度を穏やかにブースト(初期値: 1.15倍。パラメータとして後から調整可能にする)
- 軽めのCLAHE(局所コントラスト強調)で立体感を追加
- 入力: JPEG / HEIC対応。出力: JPEG(Instagram互換)に統一

いずれも「加工した感」が出ないよう、補正量は控えめなデフォルト値から始め、仕上がりを見ながら調整する。

## エラーハンドリング

- 画像として読み込めないファイル(非対応形式・破損)は加工・削除の対象外とし、「加工依頼」フォルダに残したままログに記録する
- 「加工済み」フォルダへのアップロードに失敗した場合、元画像は削除しない(データロス防止)
- 実行のたびにログ(処理件数・エラー内容)をローカルファイルに記録する
- エラーが発生した場合、`.company/secretary/todos/` の当日ファイルに通知を追記する

## 実行環境・スケジューリング

- 初回セットアップ: Google Cloud ConsoleでOAuthクライアントを作成(Google Calendar連携時と同様の手順)、Python環境構築(pip install)
- 定期実行: macOS launchd(LaunchAgent)で毎日22:00・23:30の2回実行
- 手動実行: ターミナルから直接スクリプトを実行するコマンドも用意し、急ぎの時に使えるようにする

## 組織(company)への位置づけ

- `.company/` 配下に「開発」部門を新設し、このツールの技術ドキュメント(セットアップ手順・設計)を管理する
- 生成物(加工済み画像)はマーケティング部門の投稿素材として利用する連携関係を持つ

## テスト方針

- 加工アルゴリズムの単体テスト: 既知の暗い/彩度不足のサンプル画像を用意し、加工後のヒストグラム・彩度平均値が改善していることを確認する
- Drive連携部分は、テスト用のGoogle Driveフォルダ(または一時フォルダ)を使ったモックまたは実際のAPIでの結合テストで、アップロード→加工→削除の一連の流れを確認する
- エラーケース(非対応形式ファイル、アップロード失敗のシミュレーション)で、元画像が消えないことを確認する

## スコープ外(今回はやらないこと)

- 背景変更・AI生成的な加工(今回の目的にそぐわないため対象外)
- リアルタイム(即時)処理。当面は1日2回のバッチ処理で十分
- ダウンロード検知による自動削除(API的に不可能なため日数ベースで代替)
